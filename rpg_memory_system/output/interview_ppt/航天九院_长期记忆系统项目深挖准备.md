# 航天九院面试：AI 游戏长期记忆系统深挖准备

> 本文严格依据当前代码整理。面试时要区分“已经实现”“当前存在的问题”和“后续优化方案”，不要把规划中的能力说成已经上线。

## 一句话介绍

这是一个部署在大模型外部的 NPC 记忆服务。系统用 Redis 保存近期对话和核心记忆缓存，用 MySQL 持久化画像、事件、反思、对话日志与 NPC 背景故事，并通过 Embedding 和余弦相似度按需召回长期记忆，最后把三层记忆组装进 Prompt 生成 NPC 回复。

## 一、完整数据流

1. 接收一条用户或 NPC 消息，根据 `user_id + project_id` 读取短期记忆。
2. 追加新消息，超过容量时只保留最后 60 条，再写回 Redis。
3. 消息数达到 60 条后，同步触发一批记忆加工。
4. 用户画像、事件分类、角色反思三个 LLM 任务使用 `asyncio.gather` 并发执行。
5. 核心事件和核心反思按文本精确去重，画像采用顶层字段合并。
6. 实体事件、长期反思和原始对话生成 Embedding 后写入 MySQL。
7. 处理完成后清空本批短期记忆，并刷新 Redis 中的核心记忆缓存。
8. 生成回复时，同时读取短期记忆、核心记忆，并对四类长期记忆执行 RAG 检索。
9. 将检索结果与当前问题拼入 Prompt，调用 NPC 模型生成回复，再把回复写回短期记忆。

## 二、关键配置与数据结构

| 项目 | 当前实现 |
| --- | --- |
| 对话模型 | `doubao-1-5-pro-32k-250115` |
| Embedding 模型 | `doubao-embedding-large-text-250515` |
| 短期记忆容量 | 默认 60 条消息，不是 60 轮对话 |
| 短期记忆过期时间 | 1 小时 |
| 记忆加工阈值 | 默认 60 条消息 |
| 核心记忆整合触发值 | 累计处理 240 条消息 |
| 记忆加工总超时 | 20 秒 |
| 模型客户端超时与重试 | 单次客户端超时 30 秒，最多重试 2 次，但流水线 20 秒总超时会先截断 |
| RAG 默认候选返回量 | 每类 `Top-K=10` |
| 最终 Prompt 长期记忆注入 | 实体事件 3 条、对话 3 条、长期反思 3 条、NPC 故事 2 条 |
| NPC 最大输出 | 500 Token |

Redis 使用两个 key：

```text
short_term:{user_id}:{project_id}
core_memory:{user_id}:{project_id}
```

短期记忆将整段消息列表序列化为 JSON，通过 `SETEX` 写入；核心记忆同样保存为 JSON，但当前没有 TTL。MySQL 是持久化层，Redis 核心记忆是读取加速缓存。

MySQL 主要有六类表：用户画像、核心事件、实体事件、核心反思、长期反思、NPC 故事、对话日志。用户画像对 `user_id + project_id` 建立唯一约束；多数记忆表分别对 `user_id` 和 `project_id` 建立普通索引。Embedding 当前存储为 JSON，不是数据库原生向量类型。

## 三、面试高频深挖问答

### 1. 为什么要分成三层，而不是把全部历史直接塞进上下文？

短期记忆解决局部连贯性，核心记忆保证画像和关键剧情不会因检索漏召回，长期记忆保存大量低频历史并按需检索。这样可以把“重要性”和“相关性”分开处理，减少无关历史占用上下文。

### 2. 为什么短期记忆选 Redis？

短期记忆访问频繁、生命周期短，Redis 的内存读写和 TTL 很适合这个场景。当前实现按用户与项目隔离，读取后追加消息并截断到 60 条，再整体写回。

要主动说明当前实现的不足：整段 JSON 读改写不是原子操作，并发请求可能发生消息覆盖，写入成本也随列表长度增加。生产环境应改用 Redis List 或 Stream，通过 `RPUSH + LTRIM + EXPIRE`、Lua 脚本或事务保证原子性，并增加用户级容量配额和内存监控。

### 3. 60 条是 60 轮吗？为什么选 60？

代码按消息条数计数，一次用户输入和一次 NPC 回复通常算两条，所以不等于 60 轮。60 是当前默认工程参数，用来平衡近期语境和调用成本，不是经过严格实验得到的最优值。更合理的做法是改成 Token 预算，并结合消息重要性动态保留。

### 4. 三个 LLM 任务如何并发？

使用单进程事件循环中的协程并发，不是多线程或多进程。画像抽取、事件分类、反思生成主要等待外部模型网络 I/O，使用 `asyncio.gather` 可以缩短串行等待时间。外层 `wait_for` 设置 20 秒总超时，`return_exceptions=True` 允许单任务异常时保留其他结果。

### 5. LLM 返回错误 JSON 怎么处理？

当前各任务直接执行 `json.loads`。解析或调用失败后捕获异常，画像降级为空字典，事件和反思降级为空列表，因此不会让整个请求直接崩溃。

当前没有严格 Schema 校验、JSON 修复和针对格式错误的二次请求。生产化应使用 Pydantic 或 JSON Schema 校验，增加去 Markdown 代码块、字段类型纠正、有限次数修复重试，并记录失败样本用于 Prompt 调优。

### 6. 用户画像“增量合并”是什么意思？

代码把数据库中的旧画像与本次抽取结果做字典浅合并，同名顶层字段使用新值覆盖，未出现的字段保留旧值。它不是逐字符追加，也不是模型自动判断所有冲突。

浅合并的风险是新结果中的空值或错误信息可能覆盖旧值，嵌套字段也会被整体替换。更好的方案是给字段增加 `value、confidence、source、updated_at`，按置信度和时间做字段级合并，对姓名、生日等稳定事实采用更谨慎的冲突策略。

### 7. 核心记忆如何更新和遗忘？

核心事件和核心反思写入时做文本完全相等去重。系统累计处理 240 条消息后检查核心记忆，如果某一类超过 20 条，就调用 LLM 合并相似项、删除冗余并重新写库。随后刷新 Redis 核心缓存，回复时直接注入最近 10 条核心事件和 10 条核心反思。

这属于压缩和整合，不是真正的时间衰减遗忘。长期记忆目前也没有 TTL、重要性衰减或自动删除。后续可综合重要性、访问频率、时间和冲突状态进行归档、降权或删除。

### 8. 四类长期记忆怎样召回？

当前问题只生成一次查询向量，然后并行检索实体事件、历史对话、长期反思和 NPC 背景故事。实体事件、对话、反思先按 `user_id + project_id` 过滤；NPC 背景故事属于全局角色知识，不按用户过滤。随后在 Python 中计算余弦相似度、降序排序并取 Top-K。

当前属于“标签过滤加向量相似度”的两阶段检索，但不是数据库原生混合检索，也没有 BM25、ANN 索引或重排序模型。

### 9. 余弦相似度召回有哪些问题？

当前实现会扫描过滤后的全部记录，时间复杂度约为 `O(Nd)`，数据量增大后延迟和内存开销会上升。代码没有最低相似度阈值，即使所有结果都不相关，也可能返回 Top-K；负相似度还会被截断为 0。

优化顺序可以是：改用 Milvus、pgvector、Elasticsearch 或支持向量索引的数据库进行 ANN 召回；增加最小相似度；融合 BM25；加入时间、重要性与访问频率特征；最后用 Cross-Encoder 或小模型重排序。

### 10. 为什么历史对话要做上下文扩展？

只召回一句话容易丢失前因后果。当前实现选相似度最高的 3 条消息作为锚点，每个锚点查询前 4 条、锚点本身和后 5 条，目标是恢复一个 10 条消息的局部对话窗口。

当前代码存在一个值得主动指出的问题：检索器把多个窗口展平成列表，而 Prompt 组装又只取列表前 3 条，可能没有完整注入锚点窗口。应返回结构化的对话组，先对重叠窗口去重，再按 Token 预算注入完整窗口。

### 11. Aliya 背景故事如何切分？

故事来自 Markdown 文件，按照二级、三级、四级标题和较长列表项进行语义切分，不采用固定长度滑窗。切分时会清理 Markdown 与 HTML 标记，过短内容被过滤，每个 chunk 保存 `story_name、content、embedding`。

当前文档实际得到 27 个 chunk，平均约 127 个字符，最短 46 个、最长 312 个。该策略能保留标题层级，但没有 overlap，长短分布也不均匀。后续可使用标题元数据加递归字符切分，并按模型 Token 而不是字符控制长度。

### 12. Prompt 如何融合三层记忆？

短期记忆作为完整近期对话传入。用户画像、核心事件和核心反思组成“核心记忆”区，直接注入。长期记忆按类别设置条数上限，实体事件、对话和长期反思各取 3 条，NPC 故事取 2 条，并携带相似度。

当前仅按条数控制，没有计算输入 Token，也没有对核心记忆设置总预算。私网小窗口模型下应先预留系统指令、当前问题和输出空间，再按“核心记忆高优先级、长期记忆按相关性填充”的方式动态裁剪。

### 13. 系统怎样处理数据库和模型异常？

模型客户端设置超时与自动重试，三个抽取任务可独立降级；数据库写入使用事务，失败时回滚。RAG 四类检索使用 `return_exceptions=True`，单类失败后该类返回空列表。

当前还有一致性隐患：存储函数捕获数据库异常后没有继续抛出，上层仍可能返回类似成功的状态并清空短期缓存。应让写库失败显式向上传播，使用批次 ID 和状态表保证幂等，并采用 Outbox、任务队列或至少“提交成功后再删缓存”的顺序。

### 14. 当前异步实现真的不会阻塞吗？

LLM API 使用异步客户端，适合协程并发。但 RAG 和部分记忆管理逻辑在 `async` 方法中调用同步 SQLAlchemy Session，数据库查询会阻塞事件循环，因此四类检索的并发收益有限。应统一改为 AsyncSession，或把同步查询放入线程池，并控制连接池与请求并发数。

### 15. 为什么选择豆包模型，换成 Qwen 会不会更好？

当前模型通过环境变量和 OpenAI 兼容接口配置，项目使用豆包 32K 对话模型与豆包文本 Embedding。选择更偏工程接入和中文任务适配，不代表它在所有场景都优于 Qwen。

Qwen 是否更好需要用同一批画像抽取、事件分类、反思生成和角色回复样本做评测，比较结构化输出成功率、角色一致性、召回后的回答正确率、P95 延迟和成本。迁移到九院私网时，可用 vLLM 部署 Qwen 等开源模型，但需要移除豆包特有参数，并重新验证 Prompt 与 Embedding 空间。

### 16. 如何适配九院私网、小上下文模型？

模型调用层已经采用可配置的 `base_url + model` 方式，接口形态便于替换为私网推理服务。真正落地还需要完成四项工作：统一私网模型协议；建立标签和向量索引；按 Token 做上下文预算；用领域数据评测和调优检索。

航空通信 API 多步调度场景还应把记忆扩展为任务状态、工具调用结果和共享事实，并增加 `agent_id、session_id、visibility_scope`。公共记忆需要访问控制和版本号，避免多个 Agent 相互覆盖或读取无权限数据。

### 17. 目前有没有多 NPC 之间直接交互？

这个实习项目的核心是单个 NPC 与玩家之间的长期记忆，不应声称已经实现成熟的多 NPC 共享记忆。当前 key 只包含用户和项目，没有 `agent_id`，NPC 故事也是全局表。多 Agent 公共记忆属于后续可迁移方向，也是校内课题重点。

### 18. 如何评估记忆系统效果？

当前代码中没有足以对外宣称的正式线上指标，因此不要编造“准确率提升多少”。可以提出一套评测方法：

- 检索层：Recall@K、MRR、nDCG、无关召回率、冲突记忆命中率。
- 生成层：事实一致性、角色设定一致性、跨会话问题正确率、幻觉率。
- 工程层：记忆加工成功率、JSON 合法率、P50/P95 延迟、Token 消耗、Redis 与数据库增长量。
- 评测方式：构造带标准答案的多轮剧本，结合规则检查、LLM Judge 和人工双盲评分。

## 四、当前实现边界，面试时建议主动说明

1. MySQL 中的 Embedding 是 JSON，召回由 Python 全量计算，不是向量数据库或 ANN 索引。
2. 当前没有 BM25、相似度阈值、MMR 去重和重排序模型。
3. Prompt 只按条数截断，没有输入 Token 预算和自动摘要。
4. 用户画像是浅合并，缺少字段置信度、来源和冲突处理。
5. 核心事件与核心反思只做精确文本去重，实体事件和对话日志没有语义去重。
6. Redis 短期记忆采用整段 JSON 读改写，并发下缺少原子性。
7. 异步接口中仍有同步数据库访问，可能阻塞事件循环。
8. 长期记忆没有时间衰减、冷热分层和自动遗忘。
9. 对话窗口召回与最终 Prompt 截断之间存在结构不一致，需要修正。
10. 当前没有可以直接引用的正式业务增益数据，效果应通过离线评测集和压测补齐。

## 五、典型问题的 30 秒总结

“这个系统不是简单把历史对话继续拼接，而是把模型外部记忆分成短期、核心和长期三层。短期记忆放 Redis，核心事实直接注入，低频历史向量化后按需召回。记忆加工通过三个异步 LLM 任务完成，RAG 先按用户和项目过滤，再计算余弦相似度。当前版本适合原型验证；规模化时我会重点补齐向量索引、混合检索、Token 预算、幂等写入和多 Agent 访问控制。”
